02 / CONSTRAINTS为什么要拆成这么多运行时？

架构不是画出来的，
是被约束塑造的

“页面能做什么、后台能活多久、密钥放在哪里”，比“选哪种状态管理”更先决定设计。
  1. 隔离Content Script 与业务页面处于不同世界，必须用消息协议协作。
  2. 生命周期Side Panel 会关闭，Service Worker 会休眠，长任务需要可恢复状态。
  3. 权限标签页、下载、定时器、通知等高权限能力应集中在后台。
  4. 安全API Key 只在后台模型网关读取，不进入 UI、Trace 与导出结果。

04 / GOLDEN PATH以一次 Browser Use 任务为线索

一条请求，穿过整个系统

01

发起

Side Panel / Workflow 发送 runtime message 与任务目标。

02

观察

Background 让 Content Script 收集页面、候选元素与语义集合。

03

规划

规则优先，LLM 兜底；每次只生成可验证的原子动作。

04

执行

点击、输入、切页、下载或提取；高风险动作先请求确认。

05

验收

用 URL、文本、元素、表格或下载结果证明真的完成。

核心循环：Observe → Plan → Act → Verify。未完成就重新观察；失败则保存 phase checkpoint，支持断点续跑。

06 / CODE MAPsrc/ 下的职责边界

新增能力，应该落在哪一层？

sidePanel/对话与高频工具入口；只维护交互状态，不持有模型密钥。
dashboard/任务、设置、工作流等复杂管理界面。
background/ModelGateway、TaskExecutorRegistry、Browser Use、下载与监控编排。
content/页面观察与 DOM 原子动作；不承担业务流程决策。
shared/类型协议、Repository、Memory、文档分块、OCR 结构化与错误模型。
offscreen/不依赖可见 UI 生命周期的 OCR 宿主。

08 / TRADE-OFFS我们得到什么，又付出什么？

没有免费架构，只有明确取舍

↔

多运行时隔离

得到：权限、安全与职责边界。
代价：消息协议、序列化和跨上下文调试更复杂。

⟳

可恢复任务

得到：Service Worker 重启后可收口，失败阶段可续跑。
代价：状态机、Trace 和幂等设计成本上升。

⌂

本地优先

得到：资料与 OCR 不必默认上云。
代价：WASM / 模型资源变重，IndexedDB 升级必须谨慎。

四条开发红线

01
通用自动化内核不写死业务 URL、菜单路径或 selector。
02
任务必须有正向验收证据，禁止“没执行但显示成功”。
03
保存、提交、删除、发送、支付等动作必须用户确认。
04
数据升级不得清空资料、Memory、任务记录与工作流。
